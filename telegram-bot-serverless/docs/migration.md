# گزارش سازگاری و انتقال بات اصلی

## وضعیت فعلی

منطق بات اصلی در پروژهٔ جدید پیاده شده است؛ دریافت متن، ویس، تبدیل ویس، تأیید موضوع، اجرای Workflow، بررسی ساخت، نمایش PR و تأیید یا رد آن مسیرهای جدا و قابل تست دارند.
مدیریت کلیدها از Mini App پیاده شده است؛ در این مرحله هیچ کلید واقعی، تست ابری یا migration اجرا نشده است.
بات اصلی و Workflowهای موجود دست‌نخورده‌اند.

## کلیدها: نگهداری در دیتابیس داخلی

طبق تصمیم صریح کاربر، کلیدهای OpenAI و GitHub در جدول `bot_credentials` نگهداری می‌شوند.
ثبت و تعویض فقط از Mini App و endpoint دارای احراز هویت پلتفرم و کنترل User ID مالک انجام می‌شود.
هیچ endpoint خواندن مقدار وجود ندارد. کد `credentials.js` مقدار را برای adapter سرویس مربوطه از SDK DB دریافت می‌کند.

این روش نیاز به Gateway یا اپ جدید لیارا را برای مدیریت کلیدها برطرف می‌کند، اما DB معادل Secrets Manager با حفاظت مستقل نیست؛ مدیران پروژه و کد آن به داده‌ها دسترسی دارند.
کلیدها در سورس، پاسخ endpointها یا لاگ برنامه قرار نمی‌گیرند. هیچ مقدار واقعی در این مرحله وارد نشده است.
مراحل ساخت جدول، انتشار، بازکردن Mini App و تست‌ها در [راهنمای مدیریت کلیدها](credentials.md) آمده است.

## تنظیمات موردنیاز

تنظیمات غیرمحرمانهٔ همان بات از فایل تنظیمات موجود به `config.js` منتقل شده‌اند: شناسهٔ کاربر مجاز، مالک GitHub و مخزن.
کلیدهای فعلی OpenAI و GitHub پس از ساخت جدول و انتشار صفحهٔ تنظیمات می‌توانند ثبت شوند؛ ساخت کلید جدید ذاتاً لازم نیست، مگر دسترسی یا اعتبار فعلی کافی نباشد.

دسترسی GitHub فقط روی همین مخزن:

- `Actions: read/write` برای اجرای Workflow و خواندن وضعیت.
- `Pull requests: read/write` برای خواندن و بستن PR.
- `Contents: read/write` برای Merge و حذف شاخهٔ مقاله.

محدودیت‌های شاخه، مجوز squash و checkهای اجباری همچنان برقرارند؛ کد آن‌ها را دور نمی‌زند. [API اجرای Workflow](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)، [API ادغام PR](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)

برای اتصال نهایی نیز CLI Access Token **همان بات اصلی** از BotFather لازم است؛ آن را فقط در login تعاملی یا Secrets سیستم استقرار وارد کنید.

## پیگیری ساخت بدون اجرای دائمی

هر تأیید یک dispatch کوتاه انجام می‌دهد و شناسهٔ دقیق Workflow Run را در DB می‌نویسد.
کد از نسخهٔ API فعلی `2026-03-10` استفاده می‌کند که پاسخ dispatch آن شامل `workflow_run_id` است؛ از حدس‌زدن اجرا بر اساس زمان جلوگیری شده است. [مرجع dispatch](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)

بعد از پایان handler هیچ کد پس‌زمینه‌ای ادامه پیدا نمی‌کند.
دکمهٔ «بررسی وضعیت» و `/status` در فراخوانی مستقل، وضعیت همان Run و سپس PR دارای خط دقیق `Workflow run: <id>` را می‌خوانند.
تغییر در Workflow فعلی، Cron، سرویس صف یا Webhook خارجی برای این روش لازم نیست. اعلان خودکار پایان ساخت جزو این پیاده‌سازی نیست.

صفحه‌بندی PRها به ۳ صفحهٔ ۱۰۰تایی محدود است تا هر handler کوتاه بماند؛ اگر PR یافت نشد، درخواست موفق تلقی نمی‌شود و بررسی دوباره ممکن است.

## ذخیره و تأییدها

جدول `article_requests` درخواست، صاحب و چت، متن، وضعیت، زمان‌ها، شناسهٔ اجرا، PR، SHA و تصمیم انتشار را ذخیره می‌کند.
هیچ اتکایی به فایل محلی یا حافظهٔ مشترک بین invocationها وجود ندارد.
schema از DSL رسمی استفاده می‌کند؛ عملیات DB با SQL پارامتری و تغییر وضعیت شرطی اتمی انجام می‌شوند. [دیتابیس رسمی](https://core.telegram.org/bots/serverless#the-database)

شناسهٔ Update درخواست را یکتا می‌کند. تغییر اتمی وضعیت مانع dispatch یا تصمیم انتشار هم‌زمان می‌شود.
Merge با SHA کامل نسخهٔ بررسی‌شده ارسال می‌شود و فقط پاسخ `merged: true` موفق تلقی می‌شود.
دکمهٔ بازبینی نیز به اثرانگشت نسخه وابسته است؛ دکمهٔ قدیمی بعد از تغییر PR، تأیید معتبر نیست.

درخواست HTTP خارجی و نوشتن SQLite تراکنش مشترک ندارند؛ تضمین دقیقاً یک‌بار برای شبکه قابل ادعا نیست.
اگر نتیجهٔ dispatch نامشخص شود، کد آن را خودکار تکرار نمی‌کند. پس از بررسی اجرا در GitHub، مالک می‌تواند `/attach <requestId> <runId>` بفرستد؛ اجرای انتخابی از نظر Workflow، شاخه، زمان و یکتایی شناسه بررسی می‌شود.
این فرمان برای بازیابی دستی است؛ تطبیق موضوع اجرای انتخابی با درخواست بر عهدهٔ مالک است.

اگر نتیجهٔ Merge یا بستن PR نامشخص باشد، بررسی بعدی وضعیت واقعی PR را می‌خواند و در صورت اتمام عملیات DB را به‌روز می‌کند.
اگر PR همچنان باز بماند، عملیات نامشخص خودکار دوباره اجرا نمی‌شود؛ باید نتیجه در GitHub تعیین تکلیف شود. خطاهای قطعیِ بدون اثر جانبی امکان تلاش مجدد دارند.

## محدودیت‌های اجرا

- handlerها فقط `sdk` و ماژول‌های خود پروژه را import می‌کنند؛ Node.js، npm runtime، فایل‌سیستم و تایمر استفاده نشده است. [ماژول‌ها](https://core.telegram.org/bots/serverless#the-module-system)
- دانلود ویس از API داخلی پلتفرم انجام می‌شود؛ سقف مستند دانلود ۲۰ مگابایت و سقف پاسخ HTTP خارجی ۳۰ مگابایت است. FormData و InputFile متعلق به SDK هستند. [فایل‌ها و HTTP](https://core.telegram.org/bots/serverless#files)
- مدل قبلی `gpt-4o-mini-transcribe`، زبان `fa` و فایل OGG حفظ شده‌اند. [مرجع OpenAI](https://developers.openai.com/api/reference/resources/audio/subresources/transcriptions/methods/create)
- عدد قطعی سقف زمان handler، حافظه و سهمیهٔ کل DB در مرجع عمومی فعلی مشخص نشده است. بدون تست واقعی نمی‌توان موفقیت هر ویس طولانی را تضمین کرد. اجرای طولانی تولید مقاله و Build در GitHub می‌ماند.
- دریافت تصویر و لینک عمومی مقاله قابلیت نسخهٔ اصلی نبود؛ این انتقال همان لینک PR و اطلاعات مقاله را حفظ می‌کند. موفقیت انتشار لیارا جدا از Merge است.

## درخواست‌ها و دکمه‌های قدیمی

فایل فعلی `telegram-bot/data/pending-articles.json` تغییر نکرده و هنوز منبع دادهٔ بات اصلی است؛ داده‌های آن خودکار وارد DB جدید نشده‌اند.
در زمان بررسی ۱۳ رکورد وجود داشت و یک تأیید موضوع هنوز منقضی نشده بود؛ چون بات اصلی فعال است، snapshot معتبر باید هنگام توقف نهایی گرفته شود.
قبل از انتقال، درخواست‌های باز باید در همان بات فعلی تکمیل شوند یا با بررسی وضعیت واقعی GitHub به DB جدید منتقل و دکمه‌های مناسب دوباره صادر شوند.
کد واردکنندهٔ سابقه و بازسازی دکمه‌های قدیمی در این مرحله اضافه نشده است؛ خالی‌بودن DB جدید به معنی انتقال سابقه نیست.

## ترتیب مرحلهٔ نهایی — هنوز اجرا نشده

1. انتشار schema، اجرای migration و انتشار Mini App و endpointهای مدیریت کلیدها؛ سپس ثبت کلیدها توسط مالک.
2. تعیین تکلیف درخواست‌های باز و نگهداری snapshot آخرین داده‌های بات اصلی.
3. توقف Polling همان بات و فعال‌کردن Serverless آن در BotFather؛ بات جداگانه لازم نیست.
4. اتصال CLI به همان بات. ابتدا انتشار schema، سپس migration و بعد انتشار handlerها؛ فعال‌کردن handler پیش از آماده‌شدن جدول باعث خطای DB می‌شود.
5. آزمایش واقعی روی همان بات: متن، ویس، لغو، ساخت، وضعیت، PR، رد و Merge با بررسی نتیجهٔ GitHub و سپس لیارا.

هیچ‌یک از این عملیات ابری یا تغییردهندهٔ بات اصلی در این مرحله انجام نشده است.
